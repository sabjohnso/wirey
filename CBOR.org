#+TITLE: CBOR: Gap Analysis and Redesign Plan
#+STARTUP: showall

* Current State (v2.0)

  CBOR is expressed through the redesigned DSL. The hand-written
  ~protocols/cbor.rkt~ and ~protocols/cbor-wire.rkt~ have been removed.
  CBOR now lives in the acceptance test (~tests/acceptance-test.rkt~)
  as a ~struct/wire~ definition with ~#:encode~ and ~#:decode~
  value-mapping functions.

  The ~struct/wire~ definition reads like a specification. The
  ~#:encode~ / ~#:decode~ functions handle the semantic mapping
  (Racket value → field hash → bytes and back). The wire structure
  definition handles the byte-level layout.

  The redesigned IR (~ir.rkt~), codec (~ir-codec.rkt~), and macro
  (~syntax2.rkt~) handle CBOR's case dispatch, cross-case variable-
  length fields, and recursive items cleanly — without the hacks
  that plagued the v1.x implementation.

* Pain Points from Implementation

  These are the actual problems encountered while building CBOR
  support, not hypothetical issues.

** Pain 1: ~syntax.rkt~ is a monolith (940+ lines)

   Every new feature required touching 5+ places in the same file:
   field clause parsing, alignment resolution, fd-expr generation,
   encode formal generation, accessor generation (3 strategies),
   match expander generation. A change in one area often broke another.

   The macro grew by accretion. Each feature (case blocks, repeated
   structs, embedded structs, enums, defaults, alignment, compute,
   contracts, present-when, terminators, bit-order) added conditionals
   to every phase. The phases interact in ways that are hard to reason
   about.

*** Root cause
    No intermediate representation. The macro goes directly from syntax
    to generated code, carrying all information in positional lists
    (12+ elements, accessed by numeric index). There is no data
    structure that represents "the fully resolved protocol" between
    parsing and code generation.

** Pain 2: Field info is a positional list

   Field information is a list of 12 elements:
   #+begin_example
   (name type width byte-order unit bit-order compute contract
    align present-when default enum)
   #+end_example

   Accessed by ~(first info)~, ~(seventh info)~, ~(list-ref info 11)~.
   Adding a new element means updating every place that creates,
   destructures, or extends these lists — which is everywhere.

   Case blocks, embedded structs, and repeated structs store markers
   in the type or enum positions using ~(list 'embedded ...)~ or
   ~(list 'repeated-struct ...)~, overloading existing slots. This
   creates fragile ~(and (pair? v) (eq? (car v) 'embedded))~ checks
   scattered throughout the code.

*** Root cause
    Should be a struct, not a list. Or better: a hash with named
    fields that can be extended without breaking existing code.

** Pain 3: Three accessor strategies

   The macro has three code-generation paths for field accessors:
   1. *Static*: compile-time byte offsets (fixed-width, no case blocks)
   2. *Dynamic*: precomputed boundary vector (variable-width, no case)
   3. *Case-driven*: full ~decode~ + ~hash-ref~ (case blocks or
      repeated structs)

   Each path has its own code for handling enums, embedded structs,
   bit-order, and variable-length fields. Bugs in one path don't
   exist in the others. Features added to one path are forgotten in
   the others.

*** Root cause
    Premature optimization. The static and dynamic paths exist for
    performance (avoid full decode when possible). But they triple the
    code surface and make every feature change 3× harder. The
    case-driven path (decode + hash-ref) is the only one that handles
    all features correctly. The other two are optimized paths that
    each support a subset.

** Pain 4: Codec handles too many concerns

   ~codec.rkt~ (622 lines) has a single ~encode~ function and a single
   ~decode~ function that each handle: bitfields, variable-length,
   conditional presence, case blocks, computed fields, contracts,
   repeated fields, repeat-until, padding, 12 field types. Each concern
   adds a ~cond~ branch to both functions.

   Adding case-block support required guarding every existing ~cond~
   branch against case-blocks: ~field-desc-unit~, ~field-desc-conditional?~,
   ~collect-bitfield-group~, etc. all needed ~(field-desc? ...)~ guards
   because case-blocks can appear in the same list as field-descs.

*** Root cause
    Mixed abstraction levels. The protocol-desc field list contains
    both ~field-desc~ and ~case-block~ items, violating the expectation
    that it's a homogeneous list. Every iteration over the list needs
    to check types.

** Pain 5: Encode direction is an afterthought

   The entire architecture is decode-first. The codec's ~decode~ is the
   primary path; ~encode~ mirrors it. But for self-describing formats,
   encode requires:
   - Discriminator derivation (what case branch to take)
   - Value transformation (negative integer → argument)
   - Count inference (array length → repeat count)
   - Inactive branch field omission (skip fields from wrong branches)

   None of these were designed into the system. They were added as
   wrapper functions outside the DSL.

*** Root cause
    The DSL describes the wire format (bytes), not the value mapping
    (Racket values ↔ bytes). Decode goes from bytes → fields → values.
    Encode should go from values → fields → bytes. The middle step
    (fields) exists for decode (it's the hash returned by ~decode~)
    but not for encode (the user provides field values directly via
    keyword args, or the ~#:encode~ function produces them).

** Pain 6: Forward references and lazy evaluation

   Self-referencing types (CBOR items contain CBOR items) require lazy
   lambda captures so the protocol-desc name is resolved after
   definition. This works but creates subtle ordering dependencies:
   ~(protocol-desc-total-size struct-name)~ fails during construction
   but works inside a lambda body.

   The ~compute~ width expressions carry ~#:data~ and ~#:offset~
   magic keys through the lookup function to support
   ~protocol-desc-total-size-at~ calls. This is a hack that leaks
   implementation details into the compute function signature.

*** Root cause
    No clean abstraction for "size of a variable-width item at a given
    position in the data." The system computes sizes in multiple ways:
    ~protocol-desc-total-size~ (fixed portion), ~compute-decoded-size~,
    ~compute-decoded-offset~, ~protocol-desc-total-size-at~. These
    overlap and sometimes disagree for protocols with case blocks.

* What's NOT broken

  - The field type system (uint, sint, float32, etc.) is clean
  - The checksum, enum, dispatch, and stack modules are well-isolated
  - The length-expr and case-block data structures are sound
  - The test suite (600 tests) is comprehensive
  - The protocol definitions (ITCH, IPv4, TCP, PCAP) work correctly
  - The CBOR decode through struct/wire actually works
  - The #:encode / #:decode value-level mechanism works

* Encoding Analysis: Why Each Wrapper Exists

  Every hand-written function in ~cbor-wire.rkt~ exists because the
  DSL cannot derive some aspect of encoding from the wire definition.

** There is no undecidable case

   Every Racket value has a unique CBOR encoding:
   - ~5~ (non-negative integer) → MT=0, argument=5
   - ~-6~ (negative integer) → MT=1, argument=5
   - ~(bytes 1 2 3)~ → MT=2, length=3
   - ~"hello"~ → MT=3, length=5
   - ~'(1 2 3)~ → MT=4, count=3
   - ~(hash "a" 1)~ → MT=5, count=1
   - ~1.1~ (flonum) → MT=7, AI=27
   - ~#t~ → MT=7, AI=21
   - ~#f~ → MT=7, AI=20

   The Racket type determines the major type. The value magnitude
   determines the argument. The argument determines additional-info.
   The chain is fully deterministic.

** What each function compensates for

   | Function | What it does | DSL gap |
   |----------+--------------+---------|
   | ~argument->ai+ext~ | Shortest encoding rule | No inverse mapping from value to discriminator |
   | ~encode-head~ | Conditional kwarg omission | ~#f~ means "encode zero" not "skip" |
   | ~encode-unsigned~ | MT=0 selection | No Racket-type → discriminator mapping |
   | ~encode-negative~ | ~-1-n~ transform | No per-branch value transform |
   | ~encode-bytes~ | Length → argument | No "derive discriminator from content" |
   | ~encode-text~ | UTF-8 + length → argument | Same as bytes |
   | ~encode-array~ | Count → argument | No count inference from list length |
   | ~encode-map~ | Count/2 → argument | No inverse of ~* 2~ in repeat expression |
   | ~encode-tag~ | Tag number → argument | Same as unsigned |
   | ~encode-simple~ | Same as argument->ai+ext | Same |
   | ~encode-float~ | Float reinterpret as uint | No per-branch type override |

** The single missing mechanism

   All of these reduce to one thing: the DSL needs a *value-to-fields*
   mapping. The ~#:encode~ option on ~struct/wire~ provides this as an
   escape hatch (user writes the mapping function). But ideally the DSL
   would derive the mapping from the wire structure definition itself,
   needing only the Racket-type → major-type table as input.

* Redesign Direction

  The pain points suggest a redesign around three principles:

** Principle 1: Intermediate representation

   Introduce a resolved protocol IR between parsing and code
   generation. The macro parses syntax into IR, resolves alignment
   and widths on the IR, then generates code from the IR. The IR
   is a proper data structure (structs with named fields), not
   positional lists.

** Principle 2: One accessor path

   Eliminate the static and dynamic accessor strategies. Use the
   case-driven path (decode + hash-ref) for everything. If
   performance matters later, add caching — but don't maintain
   three code-generation paths.

** Principle 3: Encode as first-class

   Design encode and decode as symmetric operations from the start.
   The wire structure definition should express both directions:
   - Decode: bytes → field hash → Racket value
   - Encode: Racket value → field hash → bytes

   The ~#:encode~ / ~#:decode~ value functions are the right
   mechanism. The question is whether the DSL can derive them
   (partially or fully) from the wire structure and a type-mapping
   declaration.
