* Redesign Status (v2.0)

  The v1.x implementation was replaced by a redesign built on three
  modules:
  - ~ir.rkt~ — clean IR with named structs and hash-based options
  - ~ir-codec.rkt~ — codec that walks the element tree (~250 lines)
  - ~syntax2.rkt~ — macro that parses syntax into IR (~419 lines)

  The old ~syntax.rkt~ (953 lines), ~codec.rkt~ (622 lines), and
  ~field.rkt~ / ~protocol.rkt~ / ~case-block.rkt~ / ~length-expr.rkt~
  are superseded but retained for reference.

  The hand-written ~protocols/cbor.rkt~ and ~protocols/cbor-wire.rkt~
  have been removed. CBOR is now expressed through the DSL in the
  acceptance tests.

  116 new-IR tests pass, covering ITCH, CBOR, MessagePack, BSON,
  IPv4, UDP, Ethernet, MoldUDP64, and all field types.

* Architecture

** Module Dependency Graph

   #+begin_example
   main.rkt (re-exports all)
     ├── field.rkt              (standalone)
     ├── length-expr.rkt        (standalone)
     ├── protocol.rkt           → field, length-expr, case-block
     ├── codec.rkt              → field, protocol, length-expr, case-block
     ├── syntax.rkt             → field, protocol, codec, length-expr, enum, case-block
     ├── stack.rkt              → field, protocol, codec
     ├── dispatch.rkt           → field, codec
     ├── checksum.rkt           (standalone)
     ├── enum.rkt               (standalone)
     └── case-block.rkt         (standalone)

   protocols/*.rkt → syntax.rkt only (via struct/wire)
   protocols/cbor.rkt → field, codec (direct, not via struct/wire)
   #+end_example

** Assessment
   - No circular dependencies
   - Clean layering: field → protocol → codec → syntax
   - Standalone modules (checksum, enum, case-block) are properly isolated
   - Protocol definitions depend only on the macro layer
   - CBOR is the exception: it uses codec primitives directly because
     self-describing recursive formats don't fit the struct/wire model

* Bugs

** BUG: ~define-stack~ hardcodes dispatch field name
   :PROPERTIES:
   :severity: low
   :file: [[file:stack.rkt::196][stack.rkt:196]]
   :END:

   #+begin_src racket
   #`(make-layer ws #,decode-fn
                 'dispatch-field #,accessor    ;; ← literal symbol, not variable
                 #,dispatch-table-expr))
   #+end_src

   Should be ~'#,dispatch-field~ to splice the actual field name.
   The ~dispatch-field~ slot in the ~layer~ struct is never read at
   runtime (dispatch uses the accessor function, not the field name),
   so this doesn't cause functional failures. It would be incorrect
   if anyone inspects ~layer-dispatch-field~ for debugging.

** BUG: ~#:terminator~ only works on ~alpha~ fields
   :PROPERTIES:
   :severity: low
   :file: [[file:codec.rkt][codec.rkt]]
   :END:

   ~encode-alpha!~ and ~decode-alpha~ handle ~#:terminator~, but
   ~utf8~, ~utf16~, and ~utf32~ encode/decode functions ignore it.
   The ~field-desc-terminator~ slot is populated but unused for
   non-alpha string types.

* Code Quality

** Strengths

*** Clean separation of concerns
    Each module has one reason to change. The data-driven layer
    (field, protocol, codec) is completely independent of the macro
    layer (syntax). Protocol definitions are isolated from core logic.

*** Comprehensive input validation
    ~make-field-desc~ validates all 12 keyword arguments.
    ~make-protocol-desc~ runs three validation phases:
    bitfield group alignment, variable-length forward references,
    and compute expression references.

*** Consistent naming
    Predicates: ~?~ suffix. Constructors: ~make-~ prefix.
    Accessors: ~struct-field~ convention. Query functions are
    descriptive (~protocol-desc-total-size~, ~field-desc-width-in-bits~).

*** No dead code
    All provides are consumed. No commented-out code. No orphaned
    helper functions.

*** Zero external dependencies
    Runtime depends only on ~base~. Build deps are standard
    (~scribble-lib~, ~racket-doc~, ~rackunit-lib~).

** Weaknesses

*** ~syntax.rkt~ is too large (857 lines)
    :PROPERTIES:
    :severity: medium
    :END:

    The ~struct/wire~ macro handles too many concerns in one file:
    - Field clause parsing (7 patterns including #:case, #:struct, #:align)
    - Alignment injection and resolution
    - Protocol descriptor generation
    - Three accessor strategies (static, dynamic, case-driven)
    - Encode keyword generation with optional/default/enum handling
    - Match expander generation

    *Recommendation*: Extract alignment resolution, accessor generation,
    and encode formal generation into helper modules or at least
    clearly delimited ~begin-for-syntax~ sections.

*** ~codec.rkt~ encode/decode are long functions
    :PROPERTIES:
    :severity: low
    :END:

    ~encode~ is ~95 lines with a ~cond~ dispatching on field type,
    conditional presence, case blocks, bitfield groups, and repeated
    fields. ~decode~ is similarly long.

    *Recommendation*: Extract per-concern handlers into named functions.
    The overall structure is sound but readability would improve.

*** No property-based tests
    :PROPERTIES:
    :severity: medium
    :END:

    The project standards call for "Algebra Driven Design & Property
    Testing" with QCheck. All 497 tests are example-based. Key
    properties that should be tested:
    - Round-trip: ~∀ pd vals. decode(encode(vals)) = vals~
    - Bitfield invariant: MSB and LSB encode/decode are inverses
    - Size consistency: ~bytes-length(encode(vals)) = total-size(pd, vals)~
    - Idempotence: ~decode(data) = decode(data)~ (no mutation)

*** No error-path testing for malformed input
    :PROPERTIES:
    :severity: medium
    :END:

    Tests verify correct behavior on well-formed data but do not test:
    - Truncated packets (offset + width > bytes-length)
    - Invalid field values (negative uint, oversized bcd)
    - Corrupted bitfield groups
    - Malformed CBOR (truncated items, wrong types in indefinite chunks)

    The codec will crash with ~bytes-ref: index is out of range~ on
    truncated input. This is acceptable if documented, but should be
    tested and either fail gracefully or documented as requiring
    well-formed input.

*** CBOR doesn't use ~struct/wire~
    :PROPERTIES:
    :severity: informational
    :END:

    ~protocols/cbor.rkt~ is a hand-written recursive decoder/encoder
    that uses ~wirey/field~ and ~wirey/codec~ directly. It does not
    use ~struct/wire~, ~define-dispatch~, or any macro layer.

    This is the right design choice — CBOR's recursive self-describing
    nature doesn't fit the flat-field model. But it means CBOR is
    proof that wirey's primitives are useful, not that ~struct/wire~
    can express everything.

    For wirey to truly claim CBOR expressibility through its DSL,
    ~struct/wire~ would need recursive case branches — which is a
    deeper language design problem.

* Module-by-Module Review

** field.rkt — 129 lines
   :PROPERTIES:
   :rating: excellent
   :END:

   Clean, focused, well-validated. The ~field-desc~ struct has grown to
   12 fields (name, type, width, byte-order, unit, bit-order, compute,
   contract, present-when, terminator, repeat, repeat-until). This is
   getting large but each field is justified.

** protocol.rkt — 122 lines
   :PROPERTIES:
   :rating: excellent
   :END:

   Three-phase validation is thorough. Handles both ~field-desc~ and
   ~case-block~ items in the field list cleanly.

** length-expr.rkt — 44 lines
   :PROPERTIES:
   :rating: excellent
   :END:

   Minimal and focused. ~field-ref~ and ~compute~ are the right
   abstractions.

** codec.rkt — 622 lines
   :PROPERTIES:
   :rating: good
   :END:

   Handles enormous complexity: bitfields (MSB/LSB), variable-length,
   conditional presence, case blocks, computed fields, contracts,
   repeated fields, repeat-until, 12 field types. The code is correct
   but long. Could benefit from extracting type-specific encode/decode
   into a registry pattern.

** case-block.rkt — 37 lines
   :PROPERTIES:
   :rating: excellent
   :END:

   Clean data structures. ~case-block-select-branch~ handles both
   exact values and predicate functions.

** checksum.rkt — 41 lines
   :PROPERTIES:
   :rating: excellent
   :END:

   Correct RFC 1071 implementation. Tested with round-trip verification.

** enum.rkt — 36 lines
   :PROPERTIES:
   :rating: excellent
   :END:

   Clean macro. Bidirectional hash tables. Pass-through for unknown values.

** syntax.rkt — 857 lines
   :PROPERTIES:
   :rating: good
   :END:

   The heart of wirey. Complex but well-structured in phases:
   1. Parse field clauses (8 patterns)
   2. Inject alignment padding
   3. Resolve alignment widths
   4. Flatten case blocks + collect all field infos
   5. Generate protocol descriptor expressions
   6. Generate encode formals (with defaults, enums, optionals)
   7. Generate accessors (3 strategies)
   8. Generate match expander
   9. Emit final ~begin~ form

   The main concern is size. Each new feature (case blocks, repeated
   structs, embedded structs, enums) added conditionals throughout
   all phases. This is sustainable for now but would benefit from
   refactoring before the next major feature.

** stack.rkt — 227 lines
   :PROPERTIES:
   :rating: good
   :END:

   Clean layer/stack abstraction. Dispatch-field bug (see Bugs section)
   is cosmetic. ~compute-decoded-size~ correctly handles variable-length
   and bitfield groups.

** dispatch.rkt — 95 lines
   :PROPERTIES:
   :rating: excellent
   :END:

   Simple, focused. O(1) hash lookup.

** main.rkt — 22 lines
   :PROPERTIES:
   :rating: good
   :END:

   Re-exports everything. No dead exports. Could add ~wirey/case-block~
   to the re-exports for completeness.
