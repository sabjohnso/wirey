#+TITLE: wirey Plan
#+STARTUP: showall

* What wirey is

  A Racket-native specification language for binary wire protocols.
  Describes the wire format declaratively; generates encoders, decoders,
  accessors, and match expanders from the description.

  Must handle fixed-layout protocols (ITCH, IPv4, TCP) and
  self-describing recursive formats (CBOR, ASN.1 BER) through the
  same DSL.

  *The project is a failure* if it cannot be used to implement all
  of the following cleanly:
  - CBOR (RFC 8949) — self-describing, recursive
  - MessagePack — self-describing, recursive, similar to CBOR
  - BSON — length-prefixed documents with type tags
  - ITCH 5.0 with full network stack (Ethernet → IPv4 → UDP →
    MoldUDP64 → ITCH message dispatch)

  "Cleanly" means: through the DSL, not through hand-written codecs
  that happen to live in the repo. The protocol definition should
  read like a specification, not like imperative Racket code.

  More broadly: anything that can be implemented with ASN.1 + ACN
  should be implementable with wirey. ASN.1 provides the type system
  (integers, strings, sequences, choices, tagged types, recursive
  types). ACN provides the encoding annotations (bit/byte order,
  field sizes, alignment, endianness, encoding rules). wirey must
  cover both roles in a single Racket-native DSL.

* Current situation

  - 600 tests pass
  - The feature set is broad: bitfields, variable-length, case dispatch,
    recursion, computed fields, contracts, enums, padding, alignment,
    defaults, 12 field types, protocol stacks, message dispatch, CBOR
  - The implementation is structurally unsound: the macro bypasses its
    own data-driven layer, carries a parallel representation (positional
    lists), and has three accessor code paths that each support a
    different subset of features
  - There are no downstream users
  - The protocol definitions (ITCH, IPv4, TCP, PCAP, CBOR) exist as
    test fixtures to exercise the DSL, not as features of the project

* What went wrong

  The original design had two layers:
  1. Data-driven: ~field-desc~, ~protocol-desc~ — the intermediate
     representation
  2. Macro: ~struct/wire~ — parses syntax, builds the IR, generates
     code from it

  In practice, the macro stopped using the IR. It parses syntax into
  12-element positional lists, resolves alignment and widths on those
  lists, and generates code directly from them. The protocol-desc is
  produced as a side output, not as the central artifact that drives
  code generation.

  Result: every new feature required changes to 5+ places in a 940-line
  macro, three accessor code paths, and the codec — all operating on
  different representations of the same information.

* Redesign principles

** The data-driven layer is the intermediate representation

   The macro's ONLY job is to parse ~struct/wire~ syntax into
   ~protocol-desc~ (and related data structures). ALL code generation
   — accessors, encode, decode, match expanders — derives from the
   protocol-desc. The macro does not compute offsets, does not choose
   accessor strategies, does not build encode formals. Those are
   responsibilities of the code-generation layer, which operates
   entirely on the data-driven IR.

** One path, not three

   There is one accessor implementation: decode the protocol-desc and
   extract the field by name. No static-offset path. No boundary-vector
   path. One path that handles all features. If performance matters
   later, add caching at the decode level — don't duplicate the code
   generation.

** Encode and decode are symmetric

   The wire structure describes both directions:
   - Decode: bytes → field values (hash)
   - Encode: field values (hash) → bytes

   For self-describing formats, a value-mapping layer sits on top:
   - Decode-value: bytes → Racket value
   - Encode-value: Racket value → bytes

   The ~#:encode~ and ~#:decode~ options on ~struct/wire~ provide
   the value-mapping functions. The wire structure definition
   (protocol-desc) handles the field-level encode/decode. These
   are separate concerns.

** field-desc uses named fields, not positional slots

   Replace the 12-element positional list in the macro with a proper
   struct or hash. Access by name (~field-info-compute~), not by
   index (~(seventh info)~). Adding a new field option must not
   require updating every place that creates or destructures the
   representation.

** The protocol-desc field list is homogeneous

   Case blocks, embedded structs, and repeated structs are not
   special markers jammed into a list of field-descs. They are
   part of the protocol-desc's structure, represented cleanly
   so that iteration does not require type-checking every element.

   Options:
   - A protocol-desc field list contains only field-descs; case
     blocks are a separate structural element
   - Or: a unified "protocol element" type that has variants for
     field, case-block, padding, etc. — iterated with pattern
     matching, not ~cond~ chains

* Implementation plan

  Since there are no downstream users, we can break the existing API
  freely. The protocol definitions are test fixtures — they can be
  rewritten as the DSL changes.

** Phase 1: Rebuild the data-driven layer

*** TODO Step 1: Clean IR for field descriptions
    Replace the ~field-desc~ struct with a design that accommodates all
    current features without positional overloading:
    - Core: name, type, width, byte-order
    - Units: byte or bit, with bit-order
    - Options: compute, contract, present-when, default, terminator,
      enum, repeat, repeat-until
    - Width can be: integer, field-ref, compute
    - Embedded/repeated struct references are explicit, not markers
      stuffed into the type or enum slot

*** TODO Step 2: Clean IR for protocol structure
    A protocol-desc's content is a list of *elements*, where an element
    is one of:
    - ~field-element~: a single field-desc
    - ~case-element~: a discriminator name + list of branches, each
      branch containing a list of elements (recursive)
    - ~padding-element~: explicit padding with width or alignment

    This is a tree, not a flat list. The codec walks the tree.
    No more type-checking each list item.

*** TODO Step 3: Codec operates on the element tree
    Rewrite ~encode~ and ~decode~ to walk the element tree:
    - ~field-element~: encode/decode the field
    - ~case-element~: evaluate discriminator, select branch, walk
      its elements
    - ~padding-element~: skip/zero bytes

    One recursive walk function for each direction. No special-case
    ~cond~ branches for case-blocks, padding, conditional, bitfields.
    Bitfield groups are identified during the walk (contiguous
    bit-unit fields) and handled as a unit.

*** TODO Step 4: Verify protocol definitions still work
    Rewrite the test fixtures (ITCH, IPv4, TCP, PCAP, CBOR) against
    the new IR. All 600 existing tests should pass. Protocol
    definitions may need syntax changes if the ~struct/wire~ surface
    syntax changes.

** Phase 2: Rebuild the macro

*** TODO Step 5: Macro produces IR only
    The ~struct/wire~ macro's output is:
    1. A protocol-desc (the IR)
    2. A predicate
    3. An encode function (keyword args → bytes)
    4. A decode function (bytes → instance)
    5. Accessors (one per non-padding field)
    6. A match expander
    7. Optional: ~encode-value~ and ~decode-value~ (if ~#:encode~ /
       ~#:decode~ provided)

    The macro generates these by calling into a code-generation
    library that operates on the protocol-desc. The macro itself is
    small: it parses syntax and delegates.

*** TODO Step 6: Code generation from IR
    A library (not a macro) that takes a protocol-desc and generates
    Racket definitions:
    - Encode: walk the element tree, collect field values from the
      hash, encode each element
    - Decode: walk the element tree, decode each element, build the
      result hash
    - Accessors: decode + hash-ref (one path)
    - Match: keyword-based, using accessors

    This library can be tested independently of the macro.

*** TODO Step 7: Macro field-info uses named representation
    The macro's internal field-info is a struct or hash with named
    fields, not a positional list. Adding a new field option is:
    1. Add a slot to the field-info struct
    2. Parse it in the syntax parser
    3. Map it to the protocol-desc IR
    No other changes needed.

** Phase 3: Encode symmetry

*** TODO Step 8: Inactive branch omission
    When encoding a case-block protocol, ~#f~ values for fields in
    inactive branches are automatically excluded. The encoder
    determines the active branch from the discriminator value in the
    hash, and only encodes that branch's fields.

*** TODO Step 9: Value-level encode/decode as first-class
    The ~#:encode~ and ~#:decode~ options remain as user-provided
    value-mapping functions. The generated ~encode-value~ and
    ~decode-value~ call them.

    For protocols that can derive the mapping (fixed-layout protocols
    where the field values ARE the Racket values), ~encode-value~ is
    just ~encode~ with keyword args. For self-describing formats,
    the user provides the mapping.

** Phase 4: Verify completeness

*** TODO Step 10: Acceptance tests — all four targets
    The redesign is complete when all four target protocols can be
    expressed cleanly through the DSL:

    1. *CBOR (RFC 8949)*: self-describing, recursive, 8 major types,
       variable-length arguments, indefinite-length encoding.
       Must pass all RFC 8949 Appendix A test vectors.

    2. *MessagePack*: similar to CBOR — type byte + payload.
       Integers, strings, binary, arrays, maps, nil, booleans.
       Must round-trip all MessagePack types.

    3. *BSON*: length-prefixed documents, type-tagged elements,
       embedded documents. Must round-trip basic documents.

    4. *ITCH 5.0 full stack*: Ethernet → IPv4 → UDP → MoldUDP64 →
       ITCH message dispatch (all 23 message types). Must decode
       a raw packet from Ethernet frame to ITCH field values.

    "Clean" means the protocol definition reads like a specification.
    If the definition requires hand-written Racket code beyond the
    ~#:encode~ / ~#:decode~ value-mapping functions, the DSL has a gap.
